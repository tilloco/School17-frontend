RULES
Saving tokens:
- New session: read HANDOFF.md, then find your place with: grep -n "\[ \]" PROGRESS.md | head -5. Read only that feature: grep -n "^<ID> " NEW_FEATURES_SPEC.md (e.g. "^A3 "). Read this RULES block once per session.
- Before creating any model, service, endpoint, screen or i18n key, grep for it; extend what exists.
- Never re-read a file you just wrote. Never print big files or full test output; filter with grep/head.
- After each step run only the tests for files you touched; the full suite once at the end of a wave.
- No subagents. One line in chat per finished feature.
- Finish one feature before the next. If one is bigger than expected, split it into sub-boxes in PROGRESS.md.
Done means ALL of:
1. Additive Prisma migration (never edit an applied one), authorization checks, input limits, rate limit where abusable.
2. Unit tests for pure logic; integration tests with at least one permission-denied case and one abuse-limit case. Never weaken or delete an existing test.
3. A minimal but working mobile screen (or admin page) using existing components, with uz/ru/en keys and no hard-coded strings. Backend-only is not done.
4. npm run typecheck and the related tests pass.
5. PROGRESS.md ticked; DECISIONS.md entry (continue numbering); KNOWN_GAPS.md line for anything not verified (screens never run on a device, real services never called).
6. Commit "<ID>: feature" in both repos if both changed, then update HANDOFF.md (done / exact next step, max 10 lines). Do not push.
Money rule: the platform never holds, moves, protects or refunds money. No code path, text, notification or screen may imply it does.
External services (Telegram, Expo push, AI): the feature turns itself off with a clear message when its env keys are missing. Never fake success in production. Prefer existing dependencies; note new ones in DECISIONS.md.
Honesty: never claim something works unless you ran it. Never kill processes you did not start (no taskkill).

Add the report reason "payment problem" to the existing report flow (admin queue; the admin cannot move money). Mobile "Pay" screen: amount, card number with a COPY button, holder name shown exactly (so the pupil can compare it with the name his bank app shows before sending), "I paid" + receipt.

WAVE 2 - TEACHER PULL
B1 Invite link. A teacher gets a short code, link and QR. A pupil who opens it lands on the teacher's page; one tap adds the teacher to "My teachers" (no discovery needed). The teacher sees an "invited" badge. First source wins.
B2 Public page /t/<slug>, no login, served by the backend: photo, subjects, price, rating, reviews (reviewer first name only), verified credentials, paymentTiming, "Open in app", "Book free trial". Verified teachers only; no contact details and NO card details; escape all output (XSS test); Open Graph tags so Telegram shows a preview.
B3 Credentials. A teacher adds IELTS / CEFR / university / olympiad entries with a document upload; admin verifies (A6); only verified ones show as chips on the profile and public page. Extend the existing verification flow.
B4 Free trial. 15-minute trial, one per pupil per teacher, max 3 per pupil per 30 days. No DirectPayment record, card not revealed, the call gate allows it. Teachers who offer trials rank slightly higher in discovery (small, documented weight).
B5 My students (teacher only). Per pupil: next lesson, last lesson note, homework status, payment status, quick message.
B6 Group lessons. A teacher creates a group session (title, time, 2-8 pupils, price per pupil). Pupils enroll; each has their own DirectPayment. The call room admits only enrolled pupils; max size enforced; if the teacher cancels, everyone is notified; blocks and the contact-info detector apply inside groups (a blocked pair cannot join the same group). First check how booking and calls assume 1:1; if it is more than about one session of work, split into sub-boxes and note the gap.

WAVE 4 - FREE LEARNING ENGINE
D1 Content model. Subjects, topics, questions (one language each, single choice with 2-5 options, explanation, difficulty 1-3). Only verified teachers author and publish immediately. "Report wrong answer" via the existing report system; 3 reports from different users hide the question pending admin review. The correct answer and explanation are returned only after the pupil answers. Dev-only seed of about 30 questions in two subjects marked SAMPLE; refuses to run when NODE_ENV=production.
D2 Daily practice. 10 questions per subject per local day (user time zone, default Asia/Tashkent): unseen first, then weakest topics; fewer if fewer exist. Streak = finishing one daily set; no freezes.
D3 Mistake notebook. A wrong answer creates a card due in 1 day; a correct review moves it to 3 days, then 7, then it graduates; a wrong review resets it to 1 day. Pure function with unit tests.
D4 Mock test. Timed, subject-wide, server-enforced deadline, answers revealed only on submit, result with per-topic percentage and weakest topics.
D5 Exam countdown. The pupil sets exam date and subjects; deterministic day-by-day plan (no AI), weakest topics first, recomputed after each mock.
D6 Q&A board. Pupils post text-only questions; verified teachers answer; pupils mark answers helpful. Limits: 5 questions per pupil per day, 20 answers per teacher per day; contact-info detector on all posts; asker shown by first name only; report button; helpful votes add a capped bonus to teacher ranking; every answer shows "Book this teacher".
D7 Photo-a-problem. AiProvider interface with a mock for tests and a real adapter reading ANTHROPIC_API_KEY and AI_MODEL from env (check the current docs for model names, do not hardcode). jpeg/png up to 5 MB, not stored after the request. AI_DAILY_LIMIT=5 per user plus a global AI_MONTHLY_CAP that switches the feature off. Tutor style: explain the steps, say it can contain mistakes, show "Ask a teacher" linking to D6. Send no user identifiers to the provider. Real-API behavior is unverified unless a key was available.
